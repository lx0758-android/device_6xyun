# Design

## Context

- 引导程序基于主线 U-Boot 的一个快照（2026-10 状态），本地在此基础上叠加少量补丁；不是从某个正式发布版拉出的板级分支。
- 板卡为 RK3566，启动介质以 eMMC 为主、SD 与 SPI 为备；Android 侧使用 `boot` + `vendor_boot`（头部版本 4），设备形态为**非 A/B**。
- 安全执行环境固件与平台固件由外部构建参数注入，仓库内不含二进制与密钥。
- 本次已将设备形态由 A/B 切换为非 A/B，并补齐 fastboot 存储后端与校验关闭声明。

## Goals / Non-Goals

**Goals:**

- 固化"主线快照 + 补丁"的基线策略与其可追溯性。
- 固化两处主线缺陷修复的行为契约，避免换基线后静默回归。
- 固化启动模式判定、参数注入、设备树选择与刷机通道的行为边界。
- 让 Android 侧镜像格式与本规格形成可校验的接口。

**Non-Goals:**

- 不引入自研启动脚本体系（保持在 bootstd + android 启动方式的框架内）。
- 不启用镜像签名校验与密钥体系。
- 不处理 U-Boot 侧设备树与内核侧设备树的一致性同步。
- 不在本变更内退出 A/B。

## Decisions

### D1：基线跟随主线快照，以补丁形式承载本地改动

- 理由：Android 启动所需的 `vendor_boot`、启动控制块、fastboot 能力在主线上已完整，从旧发布版起手反而要回移大量基础设施。
- 代价：基线升级时需要重新验证本地补丁是否仍适用；规格把两处关键补丁写成契约，作为升级检查项。
- 备选：锁定正式发布版 + 回移 Android 相关提交——工作量更大且偏离主线，放弃。

### D2：两处主线缺陷补丁必须随基线携带

- 未压缩内核 2 MB 对齐回退：镜像自带内核地址在默认参数下必然不满足 2 MB 对齐，就地执行会直接卡死。
- `vendor_boot` 设备树偏移：同一份代码在解析头部与取设备树两处使用了不同算法，页大小小于头部结构大小时必然偏移错误。
- 两者都属于主线实现内部不一致，长期应上游化；在未上游化之前，规格要求携带。

### D3：启动模式统一由引导控制块驱动

- 理由：`boot-recovery` / `boot-fastboot` / `bootonce-bootloader` 已覆盖恢复、fastbootd 与一次性进入引导程序三种需求，无需自定义按键逻辑。
- 代价：系统侧（recovery、update 组件）写控制块的路径必须正确，否则进不去对应模式。
- 备选：按键组合 + 自定义环境变量——不可脚本化且易误触发，放弃。

### D4：正常启动模式下始终声明"强制正常启动"

- 实施：仅当启动模式为正常时注入 `androidboot.force_normal_boot=1`，且不再以槽位信息为前提；恢复、fastbootd、引导程序模式保持不注入。
- 理由：恢复组件随厂商 Ramdisk 交付，系统以"恢复可执行文件是否存在"判定恢复模式；若不显式声明正常启动，非 A/B 设备（没有槽位信息）会一直被判为恢复模式，形成死循环。
- 代价：恢复模式必须完全依赖引导控制块触发，系统侧写控制块的路径必须正确。
- 备选：仅在检测到槽位时注入——非 A/B 下必然失效，放弃。

### D5：板型索引三方一致

- 探测结果、引导用设备树文件名、`vendor_boot` 内设备树索引三者必须由同一处定义驱动。
- 代价：内核侧设备树交付顺序成为隐式契约，需在规格中显式声明，防止"内核加一个 dtb"导致索引错位。

### D6：不启用镜像校验，引导程序侧按 NO AVB 适配

设备侧不生成校验镜像、校验分区空置，因此引导程序必须满足：

- 构建配置不启用校验库与校验命令，产物里不存在校验逻辑；
- 未启用校验时不读取校验分区，空分区、缺失分区、无校验页脚的启动镜像都必须正常启动；
- 启动状态恒为"未验证"，供系统按非锁定设备处理。

- 理由：启用校验需要引入完整密钥体系与签发流程，当前阶段收益低；且设备通过本地工具刷写，不依赖校验链。
- 代价：系统以未验证状态运行，无法用于需要设备认证的场景。
- 风险：板级配置目前只是"没有开启"，而不是"显式关闭"，上游默认值变化会静默开启校验（任务中补齐显式声明）。
- 备选：自签名 + 开发密钥——会引入密钥管理成本与管理风险，暂不采用。

### D7：刷机通道以 USB fastboot 为主、芯片下载模式兜底

- USB 控制器配置为双角色并关闭冲突的主机控制器，是 fastboot 可用的前提。
- 芯片下载模式命令依赖 SoC 级默认的引导模式寄存器地址，不依赖板级配置重复声明。
- fastboot 写入 eMMC 的后端选项已写入板级配置，保证干净检出即可复现当前固件能力。

### D8：非 A/B 与 NO AVB 同批落地

- 退出 A/B（无槽位分区、正常启动模式下始终声明正常启动）与补齐 fastboot 存储后端、显式关闭校验能力在同一批变更中完成，避免"设备侧已非 A/B、引导程序仍按 A/B 找分区"的中间态。
- 规格随之更新：原"槽位选择与槽位后缀注入"需求替换为"非 A/B 使用无槽位分区"，"强制正常启动"需求改为"正常启动模式下始终注入、其余模式不注入"。
- 后续跟踪项（不阻塞本变更）：两处主线缺陷补丁上游化、装载地址布局显式化、引导程序与内核设备树一致性。

## Risks / Trade-offs

- [基线升级导致补丁丢失] → 规格把两处补丁写成契约，升级时按契约核对；长期计划上游化。
- [defconfig 与本地构建配置仍可能漂移] → 已补入 fastboot 存储后端与校验关闭声明；干净树比对仍未执行（任务 2.2）。
- [装载地址默认值与脚本区重叠] → 记录为已知风险，后续显式规划内存布局时统一处理。
- [未验证状态影响设备认证类场景] → 明确记录，不用于需要认证的场景。
- [未来有人"顺手"打开 AVB 导致启动被拒] → 已显式关闭校验能力；若要启用，必须先产出 `vbmeta` 与完整签名链。当前实现在校验启用后对空校验数据是**硬拒绝**：设备锁定时只接受完全通过，解锁时也只接受完全通过或"校验失败"类错误，而空/无效 `vbmeta` 属于 I/O 类错误，两种情况都会被拒；且校验分支编译后不再有"恒报未验证"的兜底。
- [引导程序设备树与内核设备树不一致（USB 角色、安全内存保留）] → 已知并记录，后续单独变更处理。
- [非 A/B 改造未在真机验证] → 需要设备侧镜像齐备后按任务 3.5/3.6 联调，未验证前不归档相关结论。

## Migration Plan

1. 先补齐板级配置：fastboot 存储写入后端、显式关闭校验能力。
2. 再实施退出 A/B：关闭 A/B 使用，并在正常启动模式下始终注入"强制正常启动"。
3. 与设备侧"恢复资源进 vendor_boot"联调：正常启动、恢复模式、fastbootd 三条路径逐一验证。
4. 联调通过后再归档本变更。
