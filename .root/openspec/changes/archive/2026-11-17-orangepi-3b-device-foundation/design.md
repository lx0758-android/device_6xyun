# Design

## Context

参见 proposal.md。设计上需要同时满足四个外部约束：

- 内核是 GKI 形态，构建系统禁止"恢复即启动镜像"（`BOARD_USES_RECOVERY_AS_BOOT` 与通用内核镜像互斥）。
- 引导程序（U-Boot）只识别 `boot` 与 `vendor_boot` 两个启动分区，不识别独立的恢复分区。
- 启动镜像使用版本 4 头部，该格式不携带设备树字段。
- 刷机通过芯片厂商工具完成，分区表由参数文件驱动。

## Goals / Non-Goals

**Goals:**

- 产出一套自洽、可刷写、可被引导程序识别的镜像集合。
- 分区表、挂载表与镜像尺寸三者相互校验。
- 为下一阶段叠加硬件服务预留稳定的接入点（VINTF 片段、设备节点上下文、模块加载清单）。

**Non-Goals:**

- 不追求本阶段能开机（无任何硬件服务）。
- 不引入镜像签名校验与密钥体系。
- 不实现 OTA 升级链路（非 A/B OTA 工具链属遗留路径，暂不接入）。

## Decisions

### D1：非 A/B + 恢复资源置于厂商启动镜像

- 理由：GKI 下"恢复即启动镜像"被构建系统拒绝；版本 4 头部的独立恢复镜像无法携带设备树；引导程序也不识别恢复分区。把恢复组件放入厂商 Ramdisk 是 AOSP 对 GKI 设备的推荐做法，且不占用额外分区。
- 代价：恢复组件与正常启动共享同一份厂商 Ramdisk，体积变大且无法独立更新。
- 备选：独立恢复分区 + 独立恢复镜像——在当前引导程序上无法启动，放弃。

### D2：不启用镜像校验，校验分区空置保留

- 理由：启用校验需要完整密钥体系与签发流程；当前刷写工具不依赖校验链。
- 实施：关闭校验相关构建开关，不生成校验镜像，分区表中保留一个空置的小分区作为未来启用时的占位。
- 代价：系统以未验证状态运行，不能用于设备认证场景；该语义已由引导程序规格记录。

### D3：分区参数表由脚本生成，分区名不带槽位

- 参数表采用芯片平台要求的命令行分区描述格式，起始偏移与引导阶段分区尺寸固定。
- 非 A/B 下分区名不带槽位后缀，生成脚本的"自动追加第二槽位"逻辑不触发。
- 分区名与挂载表必须逐字一致，否则首阶段找不到设备节点。

### D4：分区尺寸按实测产物确定

| 产物 | 实测体积 | 分区尺寸 | 依据 |
|---|---|---|---|
| 内核镜像 | 约 42.5 MiB（未压缩） | 启动分区 64 MiB | 留出头部与页对齐余量 |
| 内核模块 | 约 19 MiB | 厂商启动分区 64 MiB | 含 Ramdisk、设备树与恢复组件余量 |
| 设备树叠加 | 约 114 KiB（两个板型） | 4 MiB | 平台惯例 |
| 元数据 | 空 | 4 MiB | 加密密钥目录预留 |
| 缓存 | 空 | 1 GiB | 恢复日志持久化、非 A/B OTA 包暂存 |

### D5：动态分区容器与组尺寸沿用已验证取值

- 容器固定 4 GiB；组尺寸取约 2 GiB（元数据预留后）。
- 理由：该组合已通过实际刷写验证；非 A/B 理论上可以放宽组尺寸，但容量提升需要重新验证刷机与首阶段解析，不在本阶段冒险。
- 后续可在独立变更中评估提升。

### D6：内核与模块集成的两条硬规则

- 模块加载清单必须过滤测试类模块：这些模块引用白名单外的符号，加载失败会导致首阶段直接崩溃。
- 模块不得裁剪：裁剪会破坏模块签名，Android 17 对白名单外符号要求签名校验，裁剪后模块会被拒绝加载。

### D7：恢复能力的可用性不依赖硬件服务

- 恢复环境自带渲染实现，直接使用内核图形驱动；因此本阶段虽无硬件服务，恢复界面仍可显示。
- 前提是图形驱动模块包含在厂商 Ramdisk 中——属于模块清单的一部分。

### D8：宽容模式是阶段性妥协

- 本阶段全部策略违规只记录不阻断，目的是把"能否启动"与"策略是否完备"两个问题解耦。
- 收紧策略必须作为独立变更实施，并在规格中同步更新，避免宽容模式被长期默认化。

### D9：设备清单空壳 + 服务自带片段

- 设备清单与兼容矩阵保持空壳，硬件服务在下一阶段通过自带清单片段声明。
- 好处：增加或删除服务时不需要改动设备清单，减少合并冲突。

## Risks / Trade-offs

- [无硬件服务导致无法开机] → 预期内；验收标准限定为"编译通过 + 镜像齐全"。
- [恢复界面无显示] → 依赖内核图形驱动模块；若缺失需检查模块加载清单而非改动设备配置。
- [分组容量偏保守] → 记录可提升空间，后续独立变更验证。
- [校验分区空置被误以为已启用校验] → 规格明确"不启用校验"，并在引导程序规格中记录未验证状态语义。
- [宽容模式被长期保留] → 规格要求收紧必须走独立变更。
- [分区名与挂载表不一致导致首阶段挂载失败] → 任务中包含逐项比对。

## Migration Plan

1. 先补齐产品定义与单板构建配置，使午餐选择可用。
2. 再落地参数表生成、镜像规则与挂载表，产出完整镜像集合。
3. 与引导程序侧联调分区名与装载地址；与内核侧确认发布目录结构。
4. 通过后进入硬件服务阶段。
