# Design

## Context

- 目标板卡为 RK3566（OrangePi-3B），Android 17 使用 6.18 GKI 内核，仓库以 `common-android17-6.18` manifest 组织为多仓（`common`、`build/kernel`、`common-modules/*`、`u-boot` 等）。
- 只有 `common` 仓库存在本地移植改动；`build/kernel`（kleaf）保持上游原样，因此构建行为完全由 `common/BUILD.bazel` 描述。
- 板卡支持两个硬件板型（v1.1 / v2.1），二者共用同一内核镜像，差异只在设备树。
- 设备侧（AOSP）以 `Image`、`*.dtb`、`*.ko`、`modules.load` 为输入，不感知内核内部结构。

## Goals / Non-Goals

**Goals:**

- 让内核移植完全等价于「厂商给 GKI 加一块新板」的标准流程：共享内核 + 板级模块 + 板级符号白名单。
- 让共享内核的本地改动收敛到最小平台使能集，便于后续跟随 AOSP GKI 升级。
- 让产物契约稳定，下游设备配置只依赖发布目录。

**Non-Goals:**

- 不引入板级独立内核镜像（不产出板级 `vmlinux`）。
- 不改动 kleaf 构建工具本身。
- 不在本次覆盖 GPU、视频编解码、WiFi/BT 等尚需驱动移植的能力。
- 不处理 U-Boot 侧设备树与内核侧的不一致（`dr_mode` 仍为 host、无安全内存保留），该项另行跟踪。

## Decisions

### D1：采用 mixed build，而不是板级独立内核

板级只有设备树与模块，没有自己的内核镜像，共享内核统一由 GKI 目标构建。

- 理由：与手机厂商使用 GKI 的方式一致；共享内核升级时板级只需重建模块；满足 Android 17 的 KMI 要求。
- 备选：维护板级独立内核（老式板级 BSP 路线）——与 GKI 方向背离，且需要长期自行合入安全补丁，放弃。

### D2：共享内核只允许平台使能改动

只允许 SoC 架构支持、PCIe 主机控制器、IOMMU 三类平台使能项，以及串口 UART 计数修复。

- 理由：这些能力必须存在于共享内核（板级没有 `vmlinux` 可承载）；其余外设都能以模块形式提供，放进共享内核会扩大升级成本。
- 备选：把所有 Rockchip 相关配置都写进共享内核——会让共享内核越来越像板级内核，放弃。
- 注意：串口 UART 计数的修复必须在共享内核配置侧完成，写进板级配置无效（板级配置无法覆盖内核内建初始化顺序）。

### D3：板级配置一律 `=m`，复合模块成员例外

- 理由：mixed build 下板级 `obj-y` 会被构建系统静默丢弃，表现为「配置看起来生效、功能却没有」，极难排查。
- 例外：会合并成单个模块的复合驱动成员保持内建，否则会被拆散成多个模块，模块清单与运行时行为都会变化。

### D4：板级符号白名单按厂商命名并纳入共享内核导出集

- 采用厂商标识作为白名单名（当前厂商标识为 `6xyun`），与手机厂商用厂商名而非机型名的惯例一致；后续同厂商新增设备可复用或扩展。
- 白名单同时用于两处：注册到共享内核的附加导出符号集合（决定裁剪后保留哪些导出），以及板级模块链接校验。缺任一侧都会导致「共享内核裁掉符号 → 板级模块未定义符号」或「ABI 校验失败」。
- 白名单由内核构建工具从最终模块产物提取，不手工维护；板级没有 ABI 基线更新目标，只有符号提取与白名单更新。

### D5：eMMC 频率以稳定性验证结果为准（150 MHz）

- 理由：该板卡的 eMMC 在控制器规格上限频率下不稳定；降频后稳定，属于已接受的性能换稳定性取舍。
- 备选：保持规格上限频率并调整时序参数——问题定位成本高且收益有限，暂不采用。
- 该决定写入规格，避免后续「优化」时被误改回上限频率。

### D6：保留尚未移植驱动的设备树节点

- 理由：这些节点与对应硬件描述是一体的，删除会让后续驱动移植重新补写；当前无驱动匹配不影响启动。
- 代价：设备树存在无驱动节点，评审时需明确「已知且有意保留」。

### D7：保留引导配置明文打印

- 理由：排期内的主要调试手段是串口日志，引导配置核对频率极高；关闭会显著增加排查成本。
- 代价：日志可能包含设备序列号等标识信息，规格中记录该风险与评审要求。

### D8：设备树强制 USB 双角色模式

- 理由：Android 侧需要外设角色（调试、刷机、文件传输），固定主机模式会直接阻断这些能力。
- 已知不一致：U-Boot 侧设备树仍为主机模式，属于引导阶段独立配置，另行跟踪，不在本变更修正。

## Risks / Trade-offs

- [共享内核被逐步「板级化」] → 规格限定共享内核只允许平台使能改动，评审时按此判定。
- [板级 `=y` 静默失效] → 规格强制 `=m`，并在构建后核对模块清单。
- [符号白名单与 ABI 基线不同步] → 规格要求成对更新，构建期的 ABI 校验作为守门。
- [调频等稳定性妥协被后续误改] → 写入规格并保留原因说明。
- [调试日志泄露标识信息] → 规格要求记录该输出为调试用途，生产构建评审时显式确认。
- [设备树与 U-Boot 侧不一致导致角色/内存保护差异] → 已知并记录，后续单独变更处理。

## Migration Plan

1. 在 `common` 中按「平台使能配置 → 板级配置 → 构建目标 → 符号白名单与 ABI 基线 → 设备树」的顺序分批提交，避免单次巨型提交。
2. 先构建共享内核，再构建板级（白名单变更会改变共享内核导出集，顺序不可颠倒）。
3. 设备侧改为引用发布目录产物；旧的板级独立内核路径不再使用。
